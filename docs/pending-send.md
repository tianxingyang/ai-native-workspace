# Recovering pending sends on the same device

The shared IM interface persists one pending send per conversation in IndexedDB before making the message POST. The encrypted intent contains the original event ID, body, optional reply and text attachment, exact scope and membership generation. A failed storage write prevents that attempt from being sent; there is no plaintext or memory-only fallback. An earlier attempt may still have an unknown outcome.

After refreshing the page, reconnect with the same valid credential to the same service and browser profile. Current readable scopes supply the recovery material. A recovered intent first checks the original send receipt. A missing receipt remains unknown; sending again requires an explicit Retry action and current send permission. Accepted messages reconcile to their current edited/retracted server state. Acknowledgement removes only the matching event ID; a failed deletion may cause another harmless receipt check after reload.

## Isolation and lifecycle

- The private session response derives a domain-separated 256-bit recovery key from the current token, persistent service epoch, authenticated actor, exact scope and membership generation. This key cannot authenticate to the service. Tokens, recovery keys and CryptoKeys are never persisted by the client.
- AES-GCM uses a fresh 96-bit IV and authenticated version/slot/event/expiry metadata. IndexedDB contains only an opaque key hash, event ID, expiry, IV and ciphertext. Message content, attachment names, scope and member identity are encrypted. Recovery keys are available only through a currently authenticated readable session. Encryption protects stored records, not an already-authorized process, captured key or compromised page.
- Expiry is bounded by the read grant and credential deadline, stored in server time and checked against the current server-adjusted clock on every access. The application independently enforces current scope deadlines. Expired records are removed during access/writes; there is no background erasure service while the app is closed. Unobserved ciphertext for old credentials or removed scopes can remain until subsequent cleanup. Clearing browser storage also removes recovery data.
- Ordinary service restart retains the epoch. Explicit backup restore rotates it. New clients attach `expectedSendEpoch` to sends, checked before deduplication; a pending or in-flight send from an older epoch is rejected. Legacy API callers may omit this optional field and retain the old API behavior. Membership-generation checks remain independent.
- Refresh/pagehide closes the in-memory connection but retains committed ciphertext. Logout, credential failure, read loss and scope-key replacement invalidate the active store and attempt conditional deletion of records it observed. Cleanup never deletes a replacement intent created by another instance. Logout is local UI cleanup, not cross-tab or server credential revocation; other still-authorized windows remain independent.
- Multiple tabs sharing a profile cannot overwrite different pending event IDs in the same slot. Transactional compare-and-set rejects that conflict; same-ID retries must preserve the complete payload. A window with a conflicting unsaved draft must wait for the other intent to resolve or reconnect to inspect it. At most 100 live encrypted slots are retained per origin.

The Tauri interface uses the same module and obtains recovery material through its existing authenticated session bridge. A newly launched demo creates a new temporary service/credential and does not recover a previous demo's outbox. Installed WebView reload/restart behavior has not been newly certified by this slice; Chromium and the existing native bridge tests are the local validation boundary.

This increment covers pending message sends, including text attachments and reply identity. It does not persist unsent composer drafts, read positions, synchronization baselines/cursors, edits/retractions, membership operations or a multi-message queue. It does not provide background automatic delivery or cross-device outbox synchronization. VIT-104 remains in progress.
