# Scoped text attachments

The IM composer accepts one nonempty UTF-8 `.txt` or `.md` file up to 8,192 bytes alongside a required message caption. Names are display labels, never filesystem paths. Markdown and HTML remain literal text. UTF-8 decoding is strict and preserves a BOM; binary controls and unpaired surrogates are rejected. No new dependencies, public URLs, downloads, or automatic execution are introduced.

`POST /messages` accepts an optional `attachment: {name, text}`. Existing send authorization and membership generation checks apply. The message contains only `{name, bytes, sha256}` metadata; the content is stored separately in the same atomic SQLite state snapshot. The new send fingerprint hashes the caption, scope, optional reply and attachment metadata, without retaining attachment text. Ordinary messages retain their existing retry identity. A failed persistence or capacity check rolls back both message and attachment. HTTP requests remain limited to 64 KiB and snapshots to 8 MiB; the shared composer also respects the desktop bridge's 60,000-byte request limit.

`GET /attachments?conversationId=…&threadId=…&messageId=…&expectedMembershipGeneration=…` requires authenticated, current read permission for that exact scope and the current membership generation. It returns `{attachment, text}` as no-store JSON. It never accepts a filesystem path or public resource URL. Caption edits preserve the attachment; retracting the message removes its current metadata and content atomically. A retry returns the current tombstone rather than restoring the attachment. This removes it from current application state; it does not promise forensic erasure from SQLite pages, previously made backups, or recipients' copies.

Ordinary member access treats people and Agents equally. A private-mode request containing `runId` additionally requires the current worker lease, live run authorization, context and scope, and consumes the existing tool budget. Lease/instance headers without `runId` are rejected. Failed run checks never fall back to member access. Raw member credentials still permit ordinary member reads while their authorization remains valid, as on the existing message API; this increment does not introduce run-only credentials or claim to isolate every read by an old process. The current Worker tool adapter does not fetch attachment content, so its output must not be presented as attachment analysis.

Draft content and previews stay in connection memory. File selection, delayed local decoding and preview responses are fenced to the initiating connection and room cache identity. Switching rooms, losing read access or changing membership generation discards stale operations. A source revision change or retraction closes and clears its preview. A known read deadline clears cached content even offline. Late 401/403 responses still invalidate the appropriate connection/scope after the preview closes. As with message sync, a revocation cannot be observed instantly during an outage before the known deadline.

Node and Rust desktop bridges expose only the exact member lookup route. Tests cover the real Node sidecar and Rust route filtering, plus Chromium interaction at desktop and narrow widths; these are not an installed Windows WebView/manual installer validation.

Remaining VIT-104 scope includes binary/multiple attachments, attachment search and Worker tools, new independent threads, persistent client outbox/cursors, and the user's pending language decisions. This slice does not mark VIT-104 complete.
